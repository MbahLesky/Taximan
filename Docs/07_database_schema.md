# Taximan — Database Schema

## 1. Purpose

This document defines the proposed Cloud Firestore database structure for the Taximan MVP.

The schema supports both the Passenger App and Driver App, including authentication profiles, bookings, trips, payments, ratings, driver availability, and earnings.

---

# 2. Database Overview

Taximan uses **Cloud Firestore** as the main real-time database.

Main collections:

* `users`
* `drivers`
* `vehicles`
* `bookings`
* `fare_proposals`
* `trips`
* `payments`
* `ratings`
* `earnings`
* `notifications`

---

# 3. General Rules

## 3.1 Document IDs

* User document ID should match Firebase Auth UID.
* Driver document ID should match Firebase Auth UID.
* Booking, trip, payment, rating, and earning IDs should be auto-generated by Firestore.

## 3.2 Timestamps

Use server timestamps for:

* `createdAt`
* `updatedAt`
* `acceptedAt`
* `startedAt`
* `completedAt`
* `cancelledAt`

## 3.3 Location Format

Store locations as both readable text and coordinates.

```json
{
  "name": "Mile 4 Junction",
  "address": "Mile 4 Junction, Bamenda, Cameroon",
  "landmarkType": "junction",
  "city": "Bamenda",
  "state": "North West",
  "country": "Cameroon",
  "latitude": 5.9876,
  "longitude": 10.1598,
  "placeId": "bamenda_mile_4_junction",
  "source": "preset"
}
```

The passenger app currently hardcodes the supported Bamenda locations in a
list of `AppLocation` models: Commercial Avenue, City Chemist, Mobile Nkwen,
Foncha Junction, Foncha Street, Mile 4 Junction, Health Center Junction,
Bambili Square, Bambui, Upstation, and Finance Nkwen. Each address is stored
with "Bamenda, Cameroon".

# 4. Collections

# 4.1 `users`

Stores passenger profile data.

## Document ID

`users/{userId}`

## Fields

```json
{
  "id": "firebase_auth_uid",
  "fullName": "John Doe",
  "email": "john@example.com",
  "phone": "+237600000000",
  "profilePhotoUrl": null,
  "role": "passenger",
  "isActive": true,
  "defaultPaymentMethod": "cash",
  "createdAt": "timestamp",
  "updatedAt": "timestamp"
}
```

## Notes

* Used only for passenger accounts.
* Driver accounts should be stored in the `drivers` collection.

---

`drivers/{driverId}`

## Fields

  "email": "driver@example.com",

  "ratingCount": 0,
  "currentLocation": {
    "address": "Current location name",
    "latitude": 5.9876,
    "longitude": 10.1598,
    "updatedAt": "timestamp"
  },
  "availabilitySchedule": [
    {
      "day": "monday",
      "startTime": "08:00",

# 4.8 `driver_locations`

Stores live driver location updates.

## Document ID

`driver_locations/{driverId}`

## Fields

```json
{
  "driverId": "driver_uid",
  "latitude": 5.9876,
  "longitude": 10.1598,
  "heading": 120,
  "speed": 30,
  "isOnline": true,
  "isAvailable": true,
  "activeTripId": null,
  "updatedAt": "timestamp"
}
```

## Notes

* This document should be updated only when the driver is online.
* Location updates should be throttled to avoid excessive writes.
* Passenger app listens to assigned driver location during active trips.

# 5. Suggested Indexes

Firestore indexes may be needed for:

## Drivers

* `verificationStatus + availabilityStatus`
* `isAvailable + availabilityStatus`

## Bookings

* `passengerId + createdAt`
* `driverId + createdAt`
* `status + createdAt`

## Trips

* `passengerId + createdAt`
* `driverId + createdAt`
* `status + createdAt`

## Fare Proposals

* `bookingId + createdAt`
* `bookingId + status + createdAt`

## Earnings

* `driverId + createdAt`

## Notifications

* `userId + createdAt`
* `userId + isRead`

---

# 6. Data Relationship Summary

* One passenger can have many bookings.
* One booking can become one trip.
* One driver can have many trips.
* One driver can have one or more vehicles.
* One trip can have one payment.
* One trip can have one rating.
* One driver can have many earning records.

---

# 7. MVP Notes

* Use Firebase Auth UID as passenger and driver IDs.
* Keep booking and trip statuses consistent.
* Do not allow offline writes for critical ride actions.
* Use Firestore transactions or Cloud Functions for critical state updates.
* Start with cash payments, then extend to real escrow/payment gateway later.

---

# 8. Summary

This Firestore schema supports the Taximan MVP with clean separation between passengers, drivers, vehicles, bookings, trips, payments, ratings, earnings, notifications, and live locations.
